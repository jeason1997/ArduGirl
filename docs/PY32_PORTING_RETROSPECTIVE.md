# PY32 移植错误复盘

本文记录 2026-08-06 首次实现 PY32F002A 平台时实际发生的错误。目的不是描述最终实现，而是把错误模式转化为后续移植必须执行的检查项，避免在 PY32、STM32 和更多游戏接入时重复发生。

## 1. 把平台代码写进具体游戏目录

### 错误

最初把 PY32 相关适配放进 `games/arduventure/`，让具体游戏承担芯片平台职责。

### 后果

- 破坏 `game -> compat -> core/platform -> backend` 的单向依赖。
- 游戏不再是平台无关的上游源码入口。
- 每增加一个平台，都可能继续污染每个游戏目录。
- 后续更新上游源码时，平台改动与游戏补丁难以区分。

### 纠正

PY32 的启动、时钟、GPIO、显示、蜂鸣器、链接和烧录全部归入 `platform/py32/`。游戏目录只保留平台无关的入口、元数据和确有必要的游戏补丁。

## 2. 把芯片厂商库放进根 `third_party/`

### 错误

最初把 PY32 的 CMSIS、设备头和 LL 库放进根目录 `third_party/`，忽略了该目录在本项目中专门承载游戏与 Arduboy 生态上游源码。

### 后果

- 混淆游戏依赖和硬件平台依赖的所有权。
- 平台删除、升级或审计时无法按目录确定影响范围。
- 容易让其他平台构建意外依赖 PY32 库。

### 纠正

PY32 厂商快照固定在 `platform/py32/vendor/`。以后每个平台的芯片库、启动文件、链接脚本和调试配置都必须放在该平台自己的目录中。

## 3. 直接修改 Arduventure

### 错误

为了尽快让首款游戏参与 PY32 构建，曾修改 `games/arduventure/` 中的内容。

### 后果

- 把通用平台问题伪装成游戏适配问题。
- 违反上游源码默认不修改的规则。
- 无法证明其他游戏能够复用同一平台实现。

### 纠正

已将 `games/arduventure/` 恢复到原状态。平台差异进入 `platform/py32/`，Arduino/AVR 公共语义进入兼容层；只有兼容层无法表达的真实游戏问题，才能以游戏自己的编号补丁保存并记录原因。

## 4. 为每个“平台 × 游戏”增加一个构建文件

### 错误

曾增加 `platform/py32/targets/arduventure.mk`，把游戏选择写成平台与游戏的组合配置。

### 后果

若有 10 个平台和 100 款游戏，会产生最多 1000 份组合构建文件；重复内容多，新增游戏或平台需要横向修改大量文件。

### 纠正

删除组合目标文件。`tools/prepare_game.py` 统一读取已有 `game.toml`，平台 Makefile 只接收通用 `GAME` 参数。新增规范游戏不应修改 PY32 Makefile，新增平台也不应修改游戏源码。

## 5. 产生无关的 `build-asan`

### 错误

工作区中留下了本次 PY32 任务不需要的 `build-asan` 构建目录，没有及时区分既有产物、任务产物和用户明确禁止的产物。

### 后果

- 污染工作区并造成任务范围不清。
- 让用户难以判断哪些文件由本次操作产生。
- 后续诊断可能误用陈旧产物。

### 纠正

该目录已删除。PY32 构建只使用 `build/py32/<game-id>/`；不得为了方便创建新的顶层构建目录。执行清理前必须先确认目标的绝对路径和所有权。

## 6. 固件能运行，但屏幕没有输出

### 错误

最初调用 PY32 LL GPIO 配置接口时，把 PA5 与 PA7、多个按钮引脚分别合并成位掩码一次传入。该芯片的相关 LL 单元接口一次只接受一个引脚，因此 SPI 引脚没有被正确配置为复用功能。仅凭固件能链接、烧录和帧计数增长，就过早认为显示链路已经跑通。

### 后果

- CPU 主循环正常运行，但 ST7789 没有收到有效 SPI 数据。
- 编译和烧录成功掩盖了硬件初始化错误。

### 纠正

所有相关 GPIO 均逐引脚配置，并对照参考工程补齐上下拉、Gamma 表和 SPI 使能顺序。验证同时检查应用帧计数、GPIOA MODER、SPI1 CR1 和 OpenOCD 运行状态。以后“可运行”与“外设可用”必须分别给出证据；没有实机画面确认时，不能宣称显示验收完成。

## 7. 在 WSL 中反复执行根目录冷构建

### 错误

诊断 PY32 时反复运行根 `make clean` 和默认 `make`，删除 Linux 全部游戏的增量缓存，导致 WSL 每次重新构建整个游戏集合。

### 后果

- 用户执行普通 `make` 时等待明显变长。
- 无关平台和游戏被重复编译，浪费时间并扩大验证噪声。

### 纠正

PY32 冷构建只能清理或强制重建 `build/py32/<game-id>/` 范围。除非任务明确要求全仓冷构建，不得删除根 `build/`，也不得用全量构建代替目标平台验证。

## 8. 忽略 AVR 与 ARM 的普通 `char` 符号差异

### 错误

首版只验证了 Arduventure，没有把 AVR 工具链的普通 `char` 语义纳入 PY32 编译契约。切换到 Sunfire 后，负数位图数据发生 C++ 窄化错误；即使绕过编译错误，俯仰和滚转等负值判断也会静默改变行为。

### 后果

- `make flash-py32 PY32_GAME=sunfire` 在编译阶段失败。
- 问题具有跨游戏性质，却容易被误判为 Sunfire 专用问题。

### 纠正

PY32 的统一 C++ 编译选项启用 `-fsigned-char`，不修改 Sunfire，也不增加游戏专用规则。修复后 Sunfire 冷构建、链接、OpenOCD 写入和校验通过，Arduventure 强制重建也通过。

## 后续平台移植检查表

开始实现或评审任意 MCU 平台时，必须逐项确认：

- 平台代码只位于 `platform/<platform>/`，游戏目录没有芯片、屏幕或烧录逻辑。
- 厂商 SDK 位于对应平台自己的 `vendor/`，根 `third_party/` 只承载游戏与 Arduboy 生态上游。
- 根 Makefile 只有通用平台入口，不出现具体游戏名。
- 不存在“平台 × 游戏”组合配置文件；游戏由统一元数据发现。
- 上游游戏目录保持 clean；必要补丁位于游戏自己的 `patches/` 并记录原因。
- 构建产物只进入既定的 `build/<platform>/<game-id>/`。
- 定向清理不触碰其他平台和游戏的缓存。
- 交叉工具链的 `char`、`int`、对齐、回绕和 `PROGMEM` 语义已明确验证。
- 厂商 GPIO、SPI、定时器接口的参数约束逐项对照头文件或参考工程，不能仅凭相似 API 猜测。
- 编译成功、链接成功、烧录成功、CPU 运行、显示可见、按键可用和音频可听分别验收，不相互替代。
- 每增加一款代表性游戏，都验证通用构建入口，不为其增加平台特判。

## 本次复盘的验收证据

- `games/arduventure/` 和 `games/sunfire/` 均无本次平台修复产生的差异。
- Sunfire 固件尺寸为 text 17376、data 368、bss 2832 字节。
- Sunfire 已由 CMSIS-DAP/OpenOCD 完成写入，日志返回 `Verified OK`。
- 启用统一字符语义后，Arduventure 也已强制重新构建通过。
